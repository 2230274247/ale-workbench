适用版本：ALE Workbench 1.8.0（迁移头 `0016`）。本文件只覆盖 P0 的四道闸门：环境隔离、备份、恢复、升级保护。字段含义、表结构、业务路由一律未改。

## 1. 正式环境与测试环境隔离

### 1.1 两个环境

| | Production（正式） | Development / Staging（测试） |
|---|---|---|
| 用途 | 真实实验录入 | 开发、迁移测试、恢复演练、机器学习 |
| 数据库 | `ale_workbench` | `ale_workbench_test` 或任意 `*_test` |
| 环境变量 | `ALE_ENVIRONMENT=production`（默认） | `ALE_ENVIRONMENT=testing` |
| 库名变量 | 不设置（回落到 `.appcreds` 的 `ale_workbench`） | 不设置时自动为 `ale_workbench_test` |
| 原件目录 | `storage/originals/` | 自动 `storage-test/originals/` |
| 界面标签 | 生产环境 | 测试环境 |

### 1.2 硬护栏（代码强制，不靠自觉）

| 规则 | 行为 | 位置 |
|---|---|---|
| `ALE_ENVIRONMENT=testing` 但库名不以 `_test` 结尾 | **启动失败**，明确报错拒绝连接 | `backend/app/config.py: database_name()` |
| `ALE_ENVIRONMENT` 非 production/testing | 启动失败 | `backend/app/config.py: environment()` |
| 测试库默认写进 `storage-test/originals` | 测试上传不会污染正式原件 | `backend/app/original_storage.py: originals_root()` |
| 生产库执行迁移未加确认 | **拒绝执行 DDL**，只提示三步流程 | `database/migrate.py`（按实际连接的 schema 判断） |
| 恢复目标为生产库 / 不以 `_test` 结尾 | **立即拒绝** | `database/restore_db.py: guard_target()` |
| 测试库初始化目标为生产库 | 拒绝 | `database/setup_test_env.py`（原有） |
| 迁移只允许 `ale_workbench` 或 `*_test` | 拒绝其它库名 | `database/migrate.py`（原有） |

### 1.3 启动测试环境

```powershell
# 1) 建/更新独立测试库（只复制表结构与迁移台账，不复制业务数据）
backend\.venv-win\Scripts\python.exe database\setup_test_env.py --target ale_workbench_test

# 2) 用测试环境启动后端（示例端口 8011，与正式 8001 错开）
$env:ALE_ENVIRONMENT='testing'
$env:ALE_DB_NAME='ale_workbench_test'
backend\.venv-win\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8011
```

> 前端开发（`npm run dev`）连接的是 8001/8011 中你启动的那个后端。**同一时间只让一个后端占用一个库**，不要把测试后端指向 `ale_workbench`。

### 1.4 日常纪律

- 只有「录入真实实验」的进程可以使用 production；开发、试验、批量导入演练一律 testing。
- `ALE_ENVIRONMENT` 一旦设为 testing，就别再手动把 `ALE_DB_NAME` 改回 `ale_workbench`——会被代码拦住，不要绕过。

## 2. 备份

### 2.1 一次备份产生什么

```
H:\ALE_Backups\20261111T081035Z_ale_workbench_p0_drill\
  database.sql.gz      mysqldump --single-transaction 一致性逻辑备份（InnoDB 快照）
  manifest.json        清单：时间/库/软件版本/迁移版本/行数/SHA-256/附件信息
  originals\           storage\originals 的完整副本（含 quick 下的 Excel 原件）
  originals.sha256     每个原件一行 `<sha256>  <相对路径>`
  SHA256SUMS           备份目录内每个文件的 SHA-256
```

`manifest.json` 的 `status=complete` **只在全部步骤成功后写入**，所以“有 manifest 且 complete”本身就是备份成功的证明；失败会留下 `FAILED.json` 并写明失败阶段。

### 2.2 清单里有哪些与科研相关的字段

| 字段 | 含义 |
|---|---|
| `software.app_version` / `software.git.commit` / `git.dirty` | 产生这份数据时的软件版本与代码版本 |
| `database.migration_version` / `migrations_applied` / `migrations_pending` | 数据库结构版本，恢复后用于判断代码能否直接配套 |
| `database.row_counts` | 52 张表逐表精确行数（含 `processes`、`quick_runs`、`quick_revisions` 等） |
| `database.dump_sha256` | 备份文件校验值，恢复前必须匹配 |
| `database.foreign_keys` / `table_count` / `view_count` | 结构指纹，恢复后逐项比对 |
| `originals.files` / `manifest_sha256` | 附件数量与清单校验值 |

清单中**不会**出现数据库密码、JWT 密钥、邮件密码。MySQL 密码只通过临时 `--defaults-extra-file` 传入客户端，用完即删。

### 2.3 常用命令

```powershell
# 手动备份（默认 H:\ALE_Backups，自动按时间命名）
backend\.venv-win\Scripts\python.exe database\backup_db.py --reason manual

# 指定目录 / 保留天数 / 跳过附件
backend\.venv-win\Scripts\python.exe database\backup_db.py --reason manual --backup-root D:\ALE_Backups --keep 60
backend\.venv-win\Scripts\python.exe database\backup_db.py --no-originals

# 列出备份
backend\.venv-win\Scripts\python.exe database\backup_db.py --list
```

- **保留周期**：默认 30 天（`--keep N` 或环境变量 `ALE_BACKUP_KEEP_DAYS`）。只清理**同一数据库**、**有 complete 清单**、超过保留期的目录；刚生成的那份永不清理。
- **空间预检**：备份前检查剩余空间（数据量 + 附件量 + 200 MB 余量），不足直接失败，不产生半成品。
- **失败提示**：退出码 `2`，控制台 `BACKUP FAILED at stage "..."`，同时写 `FAILED.json` 与 `backup.log`。
- **日志**：`<备份根目录>\backup.log`，逐行记录 START/OK/FAILED/PRUNED，不含凭据。

### 2.4 每日自动备份

```powershell
# 注册（默认每天 02:30，保留 30 天）——需要人工执行一次
powershell -NoProfile -ExecutionPolicy Bypass -File database\install_daily_backup.ps1 -Time 02:30
# 立即试跑一次
Start-ScheduledTask -TaskName 'ALE-Workbench-Daily-Backup'
# 取消
powershell -NoProfile -ExecutionPolicy Bypass -File database\install_daily_backup.ps1 -Unregister
```

任务名 `ALE-Workbench-Daily-Backup`，以当前用户交互登录方式运行，只调用备份脚本，不迁移、不改数据。若电脑夜间关机，任务会在下次开机后补跑（`StartWhenAvailable`）。

### 2.5 备份位置建议

默认 `H:\ALE_Backups`，已满足“在项目目录之外”。**同一块硬盘仍然挡不住整机损坏**，建议再加一层：

- 定期把整个 `H:\ALE_Backups` 复制到移动硬盘/另一台机器（保留目录名，不要打散）。
- 或用 OneDrive/坚果云等同步其中一个子目录；注意 `database.sql.gz` 含真实实验数据，需自行确认云端加密与账号安全。

## 3. 恢复

### 3.1 允许与禁止

| 目标 | 结果 |
|---|---|
| `*_test` 结尾、且不等于生产库 | 允许（不存在则创建；存在需 `--replace`） |
| `ale_workbench`（生产） | **永远拒绝**，任何参数组合都不行 |
| 不以 `_test` 结尾 | 拒绝 |
| `mysql` / `sys` / `information_schema` / `performance_schema` | 拒绝 |

脚本还会拒绝：清单缺失或 `status!=complete`、dump 的 SHA-256 与清单不符、`SHA256SUMS` 中任一文件被改动、dump 内出现 `CREATE DATABASE` / `USE` 语句（防止一次误指向就把数据写进正式库）。

### 3.2 命令

```powershell
# 恢复到独立测试库（不存在则创建，存在则重建）
backend\.venv-win\Scripts\python.exe database\restore_db.py `
  --backup "H:\ALE_Backups\20261111T081035Z_ale_workbench_p0_drill" `
  --target ale_restore_drill_test --replace

# 只校验已有测试库与备份是否一致（不导入）
backend\.venv-win\Scripts\python.exe database\restore_db.py --backup "<目录>" --target ale_restore_drill_test --verify-only

# 顺便把附件恢复到一个目录并逐个校验
... --restore-originals-to "H:\ALE_Restore\originals"

# 校验通过后删掉演练库
... --target ale_restore_drill_test --verify-only --drop-target
```

报告写到 `<备份根目录>\_reports\restore_<时间>_<目标>.json`，退出码：`0` 通过、`3` 校验失败、`1` 被护栏拒绝。

### 3.3 恢复后校验哪些内容

1. 表数量、视图数量、外键数量与清单一致；
2. 52 张表**逐表精确行数**一致（不是 `TABLE_ROWS` 估算）；
3. 关键关联无孤儿：`quick_runs→processes`、`quick_results/quick_steps/quick_revisions/quick_imports→quick_runs`、`process_steps/process_samples→processes`、`sample_transitions/measurements→samples`、`experiment_plan_steps→experiment_plans`；
4. 修订历史：`quick_revisions` 行数与覆盖的 run 数；
5. 迁移台账：`applied_versions` 与迁移头同清单一致；
6. 附件：按 `originals.sha256` 逐文件核 SHA-256，缺失/不一致分别报出；
7. 用应用账号（`ale_app`，只读授权）真实查询一次 `quick_runs` 行数——证明“数据能被程序读出来”，而不只是 SQL 能导入。

### 3.4 真要把正式库恢复到某次备份（人工流程，P0 不自动化）

P0 明确不提供“一键覆盖生产”的脚本，正式恢复必须人工确认：

1. 用 `restore_db.py` 把该备份恢复到 `*_test` 库，确认报告 `result: passed`；
2. 停工作台（`启动工作台.cmd` 窗口或 `Stop-Process` 对应 PID），**不要停 MySQL**；
3. 另存现有生产库（`database\backup_db.py --reason before_prod_restore`），留退路；
4. 由项目负责人确认后，用管理员账号执行：
   ```powershell
   # 仅示例：请把 <备份目录> 换成实际路径，执行前必须确认库名是 ale_workbench
   & "H:\ALE_AI\mysql-server\bin\mysql.exe" -h 127.0.0.1 -P 3307 -u root -p `
     -e "DROP DATABASE ale_workbench; CREATE DATABASE ale_workbench CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci"
   ```
   然后用 `mysql.exe` 导入该备份的 `database.sql.gz`（先解压），并按需把 `originals\` 覆盖回 `storage\originals\`；
5. 恢复后必须重新执行一次 `restore_db.py --verify-only --target <演练库>` 式的核对（或直接把生产库当只读源，用 `backup_db.py` 的新备份与旧清单比对行数）；
6. 记录到 `progress_log.md`：恢复时间、备份 id、原因、核对结果。

> 注意：`storage/originals` 是内容寻址（文件名=SHA-256），覆盖回去是安全的；但**不要删除**任何原件目录，历史记录可能仍引用旧文件。

## 4. 升级前保护流程

```powershell
# 1) 只读检查（不备份、不演练），先看结论是否正常
backend\.venv-win\Scripts\python.exe database\pre_upgrade_check.py --status

# 2) 完整流程：检查 + 自动备份 + 在 *_test 副本上真实执行迁移并核对
backend\.venv-win\Scripts\python.exe database\pre_upgrade_check.py --rehearse
```

报告：`reports\p0\pre_upgrade_<时间>.json` 与同名 `.md`（含检查表、备份 id、演练结果、人工步骤）。

检查项：

| 检查 | 说明 |
|---|---|
| `database-reachable` | 连通性、MySQL 版本、主机端口 |
| `tables-present` | 表/视图/外键数量 |
| `migration-checksums` | 已应用迁移的 SHA-256 是否仍与磁盘文件一致（改过历史 SQL 会失败） |
| `migration-ledger-known` | 库里有代码不认识的迁移版本（例如回退了代码） |
| `pending-migrations` | 待应用列表；为空表示库已是最新 |
| `code-accepts-current-schema` | 用当前代码反射现有库，验证“新代码 + 旧库”是否兼容 |
| `pre-upgrade-backup` | 自动调用 `backup_db.py --reason pre_upgrade`，拿到备份 id |
| `rehearsal-*` | 把备份还原到 `ale_workbench_up<时间>_test`，真实执行迁移，核对行数保持、代码与新结构兼容（默认演练完即删库） |

只有人工确认后才执行正式迁移（需 `--confirm-production`）。启动器在 schema 不完整时拒绝启动，因此“迁移没成功却把新代码跑起来”不会静默发生。

**回滚边界**：DDL 一旦应用，MySQL 无法事务回滚；**只回退 Git 代码不安全**，旧代码可能读不懂新结构。正确姿势是“备份恢复 + 代码版本”成对回退：按 `manifest.json` 的 `git.commit` + `migration_version` 找回匹配的那一对。

## 5. 科研数据长期保护（本次未改语义，仅确认现状）

| 要求 | 现状 |
|---|---|
| 原始参数与计算结果分开 | 快录 `payload` 为权威快照；`quick_results` 只做确定性投影；`derived_results` 单独存派生值 |
| 原始记录不被计算结果覆盖 | Excel 回填必须显式 `confirm_conflicts`；每次修改前写 `quick_revisions` 全量快照 |
| 修改保留修订历史 | `quick.py:store()` 每次 update 无条件插入一条 revision（实测 83 run / 89 revision） |
| 关联不被破坏 | 依赖内部自增主键；`process_code` 等显示编号可改；95 个外键 + 删除前依赖探测 |
| 膜厚/循环/EPC 来源清晰 | `before_origin` / `after_origin` / `source`（sha256、文件、解析器、块索引）随结果保存 |
| 表征数据可关联样品与实验 | `measurements`/`measurement_points`/`instrument_datasets` 挂在 sample/process 上；本次未改 |
| 单位与字段含义一致 | 未改动任何字段定义 |

未来做机器学习训练集时，每条样本都可以沿 `quick_runs.process_id → processes` 与 `quick_revisions` 回溯到当时的原始录入。

## 7. 仍然存在的风险

1. **同盘备份**：默认备份与数据库在同一台机器。整机损坏/丢失时，若没有复制到移动硬盘或云端，数据仍会丢失。
2. **附件不在内容校验链上**：附件按 SHA-256 校验，但备份不会对原件做“数据库引用是否都有文件”的反向全量扫描（当前 `attachments`/`source_files` 为 0 行，风险尚未暴露）。
3. **迁移 DDL 非事务**：MySQL DDL 隐式提交，迁移中途断电只能靠“升级前备份 + `schema_migration_attempts` 台账 + 人工介入”恢复，不能自动回滚。
4. **单账号**：应用统一用 `ale_app`，无法按环境给不同权限；隔离靠库名与代码护栏，不靠数据库权限。将来上多设备/公网时应拆分账号。
5. **生产恢复无脚本**：正式覆盖生产必须人工执行 SQL（见 3.4），这是有意的设计取舍，但也意味着操作失误仍可能造成损失。
6. **备份未加密**：`database.sql.gz` 是明文实验数据，存放位置与访问权限需自行控制。
7. **未做异地/离机演练**：本阶段只在本机完成恢复演练，没有在“换一台电脑”上验证过完整还原（含 MySQL 数据目录、Python 环境、前端构建）。

## 8. 我日常应该怎么用

- **每天**：不用管。若已注册每日任务，凌晨自动备份，失败会写 `backup.log`；每周看一眼 `backup_db.py --list` 是否有新的 complete。
- **每次改代码/升级前**：跑 `pre_upgrade_check.py --rehearse`，看报告结论再决定是否 `--confirm-production`。
- **每次批量导入/大改数据前**：先 `backup_db.py --reason before_import`，保留 30 天足够回溯。
- **每月一次**：把 `H:\ALE_Backups` 复制到移动硬盘；随手跑一次 `restore_db.py --target ale_restore_drill_test --replace` 验证备份真能恢复，再 `--drop-target` 清掉。
- **换电脑/重装系统**：先装 Python 3.14、Node 20、MySQL 8.4（端口 3307），再按 `README` 建库建账号，最后用最新备份恢复到 `ale_workbench`（按 3.4 的人工流程），并把 `originals\` 放回 `storage\originals\`。
